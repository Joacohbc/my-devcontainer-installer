# Glosario del Dominio (Ubiquitous Language)

Este documento define el vocabulario ubicuo y las reglas de negocio de `devcontainer-cli`. Todo agente y colaborador debe utilizar estos términos de forma consistente en código, documentación y pruebas.

| Término | Código / Identificador | Definición y Reglas de Negocio |
|---|---|---|
| **Devcontainer** | `DevcontainerConfig`, `devcontainer-ssh` | Entorno de desarrollo aislado en Docker gestionado por la CLI, compuesto por un contenedor principal con SSH y herramientas de desarrollo, y opcionalmente servicios complementarios. |
| **Workspace** | `workspace`, `types.WorkspaceDir` | Directorio de trabajo del proyecto montado en el contenedor bajo `/workspaces/<workspace>`. Nunca se monta como un `/workspace` plano para evitar la colisión y mezcla del historial de sesiones de agentes de IA entre distintos proyectos. |
| **Alias de Workspace** | `types.WorkspaceAlias` | Enlace simbólico `/workspace/<workspace>` creado por el entrypoint para conveniencia al hacer `cd`, manteniendo la separación por proyecto. |
| **Módulo Dockerfile** | `dockerfile.ModuleSpec`, `catalog.DockerfileModules` | Fragmento componible de Dockerfile que instala una herramienta o lenguaje específico (ej. `nodejs`, `python`, `golang`, `bun`, `pnpm`, `github-cli`, `ai-clis`). Declara dependencias (`Requires`), conflictos (`Conflicts`), variables de compilación (`ProvidesEnv`) y variables de ejecución (`RequiresEnv`). |
| **Servicio Compose** | `compose.ServiceSpec`, `catalog.ComposeServices` | Servicio complementario en `docker-compose.yml` (ej. `postgres`, `redis`, `mongo`, `dind_engine`) que acompaña al contenedor principal en la misma red Docker. |
| **Repositorio de Configuración** | `service.ConfigRepo`, `ConfigRepoGitignore` | Repositorio git único en `~/.config/devcontainer-cli/` que versiona `profiles/`, `images/` y `skills/` mediante un `.gitignore` de lista de permitidos. Cada operación de la CLI que cambia una definición registra un commit Conventional limitado a sus rutas; nunca hace `push` y un fallo de git solo genera una advertencia. |
| **Perfil** (antes *Preset*) | `catalog.Profile`, `~/.config/devcontainer-cli/profiles/<id>/profile.yml` | Plantilla de proyecto para un caso de uso, equivalente a un `devcontainer.config.json` reutilizable: módulos Dockerfile (o una imagen de partida mediante `image`), scripts personalizados, servicios compose (`services`), volúmenes adicionales (`volumes`), variables de entorno (`env`), puertos y habilidades de agente. Las banderas explícitas prevalecen sobre el perfil (`domain.ApplyProfileTemplate`). Existen dos formas: literales integrados en Go (`plainBuiltinProfiles`) y definidos por el usuario como directorio `profiles/<id>/` con `profile.yml` y sus scripts (los archivos planos `<id>.yml` ya no se leen). En `mode=custom`, múltiples perfiles pueden apilarse mediante lista separada por comas (`--profile a,b`), generando un perfil efectivo con la unión de módulos, servicios, volúmenes, puertos y habilidades, concatenación ordenada de scripts, fusión de `env` y validación de que no haya conflictos de modo de habilidades, valores de `env` ni imágenes de partida. En `mode=profiles` y `run --profile`, se requiere exactamente un perfil remoto. |
| **Objetivo de Descarga** | `Profile.Remote`, `types.RemoteVariants` | Variante de perfil cuya imagen ya ha sido precompilada y publicada en GitHub Container Registry (`ghcr.io/devcontainer-<variant>:latest`). Permite inicio instantáneo sin compilación local. `base` (solo GitHub CLI, sin lenguaje) también es una variante publicada. |
| **Modo de Compilación** | `types.BuildModeCustom`, `types.BuildModeProfiles`, `types.BuildModeImage` | Estrategia de generación del contenedor: `custom` compila un Dockerfile local y calcula su huella digital; `profiles` omite el Dockerfile y consume directamente una imagen precompilada remota de GHCR; `image` utiliza tal cual una imagen desacoplada (una definición de imagen o una referencia de registro), sin Dockerfile; el asistente de workspace lo ofrece cuando existen definiciones (D27). |
| **Definición de Imagen** | `domain.ImageDef`, `~/.config/devcontainer-cli/images/` | Manifiesto YAML que describe una imagen reutilizable e independiente de proyectos, construible localmente o referenciada remotamente, aislada bajo el namespace `devcontainer-cli-img/<name>:<tag>`. Puede derivarse de otra imagen con `from` y es autocontenida: sus scripts viven junto a `image.yml`. Su origen (`source`) es `build` o `remote`, y el autocompletado de `image build` e `image pull` filtra por él (D26). Se ejecuta con `run --image` o en `mode=image`; `ImageService.Available` exige que una definición `build` esté construida (D27). |
| **Contenedor Quick-run** | `service.RunService`, `service.QuickRunSource`, etiqueta `dev.devcontainer-installer.quick-run` | Contenedor desechable creado por `run` o `agent run` sin archivos de proyecto. Su etiqueta guarda el origen calificado (`profile:<id>` o `image:<name>`; un valor sin prefijo se lee como perfil), y un contenedor existente solo se reutiliza para el mismo origen (D27). |
| **Imagen Derivada** | `DockerfileConfig.From`, `domain.ResolveImageParent`, `BaseRef`, `BaseModules` | Imagen (de definición o de proyecto) construida `FROM` otra imagen de la CLI, instalando solo los módulos que el padre no tiene. `From` es lo que el usuario pidió (persistido); `BaseRef` y `BaseModules` se resuelven en cada generación. |
| **Huella Digital** | `ComputeFingerprint` | Hash SHA-256 generado a partir del Dockerfile normalizado sin bloques `LABEL`, archivos copiados, módulos ordenados y UID/GID del usuario anfitrión. Nunca incluye nada específico del workspace, por lo que configuraciones idénticas comparten una única imagen. |
| **Etiqueta de Contenido** | `domain.ContentImageTag`, `devcontainer-cli/<origen>-<fp8>:latest` | Nombre de una imagen de proyecto: el origen (perfil, perfiles compuestos unidos con `-`, o `custom`) más los primeros 8 caracteres de la huella. Reemplaza a la antigua etiqueta `devcontainer-cli/<fp12>` y a la Capa de Proyecto. |
| **Origen de Imagen** | `DevcontainerConfig.Origin`, `ResolvedOrigin()`, etiqueta `dev.devcontainer-installer.origin` | De dónde proviene el contenido de una imagen (perfil o `custom`); da la parte legible de la Etiqueta de Contenido. |
| **Propietario de Imagen** | `domain.RegistryOwnerID`, etiqueta `dev.devcontainer-installer.owner` | Identificador del directorio de configuración que construyó una imagen. La recolección automática solo elimina imágenes de su propio registro, porque el daemon puede ser compartido. |
| **Clase de Imagen** | `types.ImageKindProject`, `types.ImageKindNamed`, etiqueta `dev.devcontainer-installer.kind` | `project` para imágenes construidas para proyectos (recolectables); `named` para imágenes reutilizables del módulo `image` (nunca recolectadas automáticamente). |
| **Recolección de Imágenes de Proyecto** | `PruneService.CollectProjectImages` | Eliminación por conteo de referencias de las imágenes construidas por la CLI que ningún proyecto registrado ni contenedor usa; se ejecuta tras compilar, recompilar, actualizar y destruir. |
| **Compilación Desactualizada** | `service.StaleBuildReasons` | Proyecto `custom` cuyos archivos generados difieren de lo que generaría la versión actual de la CLI (típicamente tras actualizarla). `workspace up` e `inspect status` lo advierten. |
| **Volumen de Configuración Compartida** | `devcontainer-shared-config`, `types.SharedConfigEntries` | Volumen Docker persistente con estructura plana que almacena credenciales y configuraciones de herramientas (`claude`, `agents`, `gh`, `codex`, `antigravity`, `herdr`). El entrypoint proyecta estos directorios en el home del contenedor mediante enlaces simbólicos con resolución de alias (`link_or_keep`). |
| **Contrato de Entorno de Scripts** | `script_env` (entrypoint), `DC_WORKSPACE_DIR`, `DC_WORKSPACE`, `DC_SCRIPT_PHASE`, `domain.LintCustomScript` | Variables que un script personalizado recibe según su fase (`when`): `start` y `service` reciben el directorio y el nombre del proyecto más la fase; `build` solo la fase, porque no hay proyecto montado durante `docker build`; `manual` ninguna. Son API pública de los perfiles de usuario (D25): renombrarlas rompe perfiles existentes. Un script `build` que referencia el proyecto genera una advertencia antes de construir. |
| **Entorno como Datos** | `ProvidesEnv`, `ContainerEnv` | Enfoque arquitectónico donde las variables de entorno y `PATH` se modelan como datos estructurados en Go, renderizándose simultáneamente en directivas `ENV` de Dockerfile (procesos sin shell) y en `~/.dc-env.sh` (sesiones interactivas y SSH). Nunca se escriben como `export PATH=...` en scripts de inicio. |
| **Contrato de Python en Contenedor** | `UV_SYSTEM_PYTHON`, `UV_BREAK_SYSTEM_PACKAGES` | Regla obligatoria para `uv pip install` dentro del contenedor: `UV_SYSTEM_PYTHON=1` apunta al intérprete del contenedor, `UV_BREAK_SYSTEM_PACKAGES=1` sobrepasa PEP 668, y un `chown` no recursivo sobre las rutas devueltas por `sysconfig.get_path` permite escritura a `devuser` sin `sudo`. Queda prohibido declarar `VIRTUAL_ENV` a nivel de imagen. |
| **Habilidad de Agente** | `skills.Spec`, `catalog.AgentSkills`, `skills.yml` | Integración de contexto y herramientas para asistentes de IA (`npx skills add`). Son de alcance estricto de proyecto (se instalan en el workspace) para no contaminar el volumen compartido. |
| **Wizard (`workspace init`)** | `newInitCommand`, `runGenerate` | Creador interactivo del devcontainer del proyecto; los flags dados omiten su paso. Equivale a ejecutar `devcontainer-cli` sin argumentos. |
| **Menú de acceso** | `offerUpAndAccess`, `accessOptions` | Cierre interactivo del asistente: pregunta si ejecutar `up` y luego ofrece SSH efímero, SSH con creación de clave, shell o ninguno (D23). |
| **Auto-init (`workspace auto-init`)** | `newAutoInitCommand`, `InitService` | Inicialización sin prompts: detecta el stack del proyecto, clona un repositorio opcional, construye y levanta el stack. |
| **Descubrimiento de Habilidades** | `domain.DiscoveredSkill`, `service.DiscoverSkills` | Inspección de repositorios o fuentes externas mediante Skills CLI (`npx skills add <src> --skill '*' --copy -y --json`) en directorio temporal para identificar habilidades instalables, metadatos y auditoría de seguridad Snyk sin requerir declaración manual previa. |
| **Modo de Instalación de Habilidades** | `types.SkillsMode` (`manual` o `auto`) | `manual` deja la ejecución de `install_skills` a discreción del usuario; `auto` instala o actualiza las habilidades en cada arranque del contenedor mediante `autostart-project-skills.sh`. |
| **Contexto Dinámico de Orientación** | `~/CONTEXT.md`, `domain.GenerateContext`, `domain.ContextMount` | Documento generado por proyecto a partir de las secciones `Context` declaradas por cada módulo y servicio activo, y montado en el contenedor como archivo de solo lectura (nunca horneado en la imagen). Informa al agente de IA exactamente qué herramientas, rutas y credenciales existen en el contenedor actual. |
| **Habilidad de Contexto Global** | `devcontainer-context` | Habilidad preinstalada en toda imagen que instruye a los agentes a consultar `~/CONTEXT.md` y `get-devcontainer-context`, sin duplicar detalles del proyecto. |
| **Fachada para Agentes** | `agent.go`, grupo de comandos `agent` | Subcomandos (`agent cli-info`, `create`, `run`, `ssh`, `exec`, `forward`, `list`, `destroy`) con valores predeterminados estrictos para automatización desatendida (ejecución por defecto como `devuser`, rechazo sin prompt, fallo explícito y ruidoso). |
| **Gestión de SSH Dedicada** | `SshService`, `~/.ssh/devcontainer-cli.config` | Ciclo de vida completo de conexiones SSH gestionado en un archivo de configuración propio de la CLI, incluido en `~/.ssh/config` mediante una única directiva `Include`. Fija las claves de host del contenedor para evitar advertencias de cambio de identidad tras reconstrucciones. |
| **Túnel Inverso** | `reverse:PORT`, `ssh -R` | Apertura de túnel SSH desde el contenedor hacia la máquina anfitriona, permitiendo que el contenedor acceda a servicios que corren en el host (bases de datos locales, APIs o puertos de otros proyectos). |
| **Triplete de Plataforma** | `devcontainer-cli-<triplet>` | Nomenclatura normalizada para binarios y sumas de verificación de versiones: `linux-x64`, `linux-arm64`, `darwin-x64`, `darwin-arm64`. |
